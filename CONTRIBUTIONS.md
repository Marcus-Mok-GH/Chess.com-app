# Contributing to chess.com-app\n\nThank you for helping improve this chess.com remake. Contributions are welcome when they make the app more reliable, enjoyable, accessible, or easier to maintain.\n\n## What contributors can do\n\nYou may open issues and pull requests for:\n\n- Bug fixes, regression tests, and improvements to chess rules, games, matchmaking, analysis, puzzles, authentication, or the UI.\n- Accessibility, responsive-design, performance, documentation, and developer-experience improvements.\n- New features that fit the existing product direction. For a substantial feature, open an issue first so the scope and approach can be discussed.\n- Small refactors that reduce complexity without changing behavior.\n\nWork in a fork or a short-lived feature branch. Keep pull requests focused, explain the user impact, and include tests or reproduction steps when practical. Include screenshots or a short recording for meaningful UI changes.\n\n## Limits and prohibited changes\n\nContributors must not:\n\n- Commit passwords, API keys, tokens, database URLs, OTPs, Pollen keys, or any other secret. Use local environment variables and keep real credentials out of issues, logs, screenshots, and pull requests.\n- Weaken authentication, authorization, rate limits, abuse protections, token handling, or server-side validation. Never send delegated or provider credentials to the browser.\n- Bypass the Pollinations user-pays flow, use a maintainer-owned key to pay for player requests, or change consent, budget, expiry, or token-storage behavior without maintainer approval.\n- Add analytics, tracking, data collection, or a new external service without explaining the data collected, why it is needed, and getting maintainer approval.\n- Expose, sell, or unnecessarily retain player data; use real user data in tests or screenshots; manipulate ratings, match results, matchmaking, or other competitive records.\n- Copy Chess.com proprietary code, artwork, text, sounds, branding, or other protected content. Keep new assets original or properly licensed, and do not imply official affiliation.\n- Make destructive production changes, alter deployment or environment configuration, run production database migrations, or change the database schema without maintainer approval and a documented migration/rollback plan.\n- Make breaking API or schema changes without updating the source OpenAPI/Zod definitions, generated clients where applicable, tests, and migration notes.\n- Rewrite shared history, force-push to someone else’s branch, merge your own pull request, or publish a release. Maintainers control merges, releases, production access, and repository settings.\n- Mix unrelated formatting, dependency upgrades, or drive-by refactors into a feature or bug-fix pull request.\n\nA pull request may be declined, narrowed, or closed if it creates security, privacy, licensing, operational, or maintenance risk—even if the code works locally.\n\n## Before opening a pull request\n\n1. Check existing issues and pull requests. For non-trivial work, describe the problem and proposed approach in an issue first.\n2. Follow the repository’s pnpm workspace structure and keep generated files consistent with their source definitions.\n3. Run the checks relevant to your change:\n\n   pnpm run typecheck\n   pnpm test\n   pnpm run build\n\n   If a check cannot run because it needs local services or environment variables, say so clearly in the pull request.\n4. Update CHANGELOG.md for a meaningful user-facing or operational change.\n5. Describe what changed, how it was tested, known limitations, and any deployment or migration considerations.\n\n## Review and acceptance\n\nEvery pull request is subject to maintainer review. Maintainers may request changes, ask for tests or documentation, adjust scope, defer work, or close a pull request that does not fit the project. Review approval does not grant permission to deploy or change production systems.\n\nPlease keep discussion technical and respectful. Do not post exploit details, credentials, or private user information. If you find a security issue, contact the repository owner privately through GitHub instead of opening a public issue with a working exploit.\n\n## Contribution quality bar\n\nA good contribution is focused, testable, documented where needed, and safe for users who run their own instance. When in doubt, choose the smallest change that solves the problem and ask before expanding its scope.
